# 0009: Vapi as a second phone provider, with the backend in charge

## Context

OpenAI Realtime's built-in voices did not sound natural enough on real calls. Vapi offers many more voices (ElevenLabs, Cartesia and others) and tuned turn-taking for phone calls.

## Decision

- **Vapi answers the number; the backend still decides.** On each call Vapi asks the backend for the assistant (`assistant-request`). The instructions, tools and limits come from the same code as OpenAI calls, so there is one source of truth and nothing to keep in sync in Vapi's dashboard.
- **Tools run on the backend.** Vapi sends tool calls to the same endpoint; they go through the same `run_tool` with the same validation, budgets and phone-only tools. A call's pending booking, verified booking and pending change are stored on its session record, because Vapi's requests are stateless.
- **One shared secret** authenticates every request: Vapi sends it as a bearer token from a stored credential, and per-call assistants carry it in `server.headers`.
- **OpenAI SIP stays.** Moving the number back is a Twilio setting.

## Consequences

- A per-minute platform charge on top of the model and voice costs.
- Replies go speech-to-text → model → text-to-speech, which can add latency compared with Realtime; Vapi's endpointing and streaming keep it close.
- Vapi's own analytics (recordings, transcripts) live in Vapi. The backend stores only the session outcome and Vapi's reported cost, as for other calls.
